# 5 · kiste — Reading

> The chest: a box you open, not a box you post through.

Fuglekasse stays as it is. Minimal is a feature with a fence, and the fence holds — flat templates,
inline CSS, no assets pipeline, no JavaScript beyond the small handful already there. Every request
to make it "just a bit richer" is a request to make it something else.

So growth gets its own house. A second theme, **Postkasse**, wearing the name of the cycle that
dreamed it, chosen by a one-line `theme:` key in `hugo.yaml`. Inside Postkasse, and only there:
search, backlinks, honest RSS. `bin/build.sh` never learns that a second theme exists.

Reading follows capture on purpose — the richer site should launch with richer content.

## Dependencies

**suitcase first, ideally.** Search over eleven records is a demo; search over a decade of imported
conversations is the feature.

Item 1 gates 2, 3 and 4 — they all live inside the new theme.

## Items

### 1 · flue — Postkasse, the skeleton

A second theme grown from Fuglekasse's flat shape, not a fork left to drift.

- `tools/hugo/themes/Postkasse/` with `layouts/baseof.html`, `home.html`, `page.html` and the same
  `_partials/` contract — `record.html` takes the same dict, `repo-link.html` resolves the same
  shapes.
- Its own `hugo.toml` `[params]` defaults, following the existing three-layer rule: theme toml →
  site `hugo.yaml` → `HUGO_PARAMS_*`.
- Selected by `theme: Postkasse` in `tools/hugo/hugo.yaml`, one line, nothing else changed.
- All four pageModes work, or the theme documents which it supports and warns on the rest — the same
  `warnf`-and-fall-back discipline `home.html` already uses.
- A `README.md` documenting every param it adds, mirroring the Fuglekasse README's shape.
- Postkasse may have an assets pipeline and may have JavaScript. That is the entire point of it
  being a different theme.

**Files:** `tools/hugo/themes/Postkasse/`, `tools/hugo/hugo.yaml` (commented example),
`docs/customize` prose as needed.

**Acceptance:** `theme: Postkasse` builds a complete site with `hugo --minify`, no template
warnings, and switching back to Fuglekasse produces byte-identical output to today.

**Border:** the PDF and EPUB read `records/` and the site config, not the theme. `book.lua` must not
gain a Postkasse branch.

### 2 · beetle — Site-wide search

The thing a chest of a thousand conversations actually needs.

- Build-time index: a JSON file generated by a Hugo output format over `site.RegularPages`, holding
  title, date, tags, permalink and the searchable text with signature lines stripped.
- Client-side query, no service, no external script. A few hundred lines of vanilla JS in the theme.
- Index size is the real constraint — measure it at 1 000 and 10 000 records (badstu item 6 has the
  corpus) and decide then whether the index needs splitting or truncating. Document the number.
- Degrades without JavaScript to the existing filter and TOC.

**Acceptance:** a query against a 1 000-record corpus returning correct hits, with the index size
reported.

### 3 · cricket — Backlinks, computed at build time

Records reference each other. Right now that reference is one-directional and invisible from the
other end.

- At build time, collect every internal link between records and render a "referenced by" block on
  the target page.
- Hugo can do this with `.Site.RegularPages` and a scratch map; no JavaScript needed, which means
  this one could arguably live in Fuglekasse — it does not, because the fence is the fence.
- Relative `records/` links are already rewritten to forge raw URLs by `record.html`; the backlink
  pass must run on the source text, before or independently of that rewrite. Get this right or the
  graph will be empty.

**Acceptance:** two records linking to a third, both listed under it, with the forge-rewrite
untouched.

### 4 · moth — RSS, done right

RSS is disabled site-wide for a good reason: the embedded template leaks signature lines through
summaries. That is a template problem, not a feed problem.

- A feed template inside Postkasse that strips signature lines the same way `record.html` does — one
  regex, one place, shared if possible.
- Flip `disableKinds` knowingly in the site config, documented as a Postkasse-only setting.
- Full-content vs. summary: pick one, justify it in the README. Summaries of conversations are
  usually useless; full content is honest.
- Fuglekasse keeps RSS disabled. Unchanged.

**Acceptance:** a validated feed containing no `— model-name` lines, checked against a record that
has them.

### 5 · tadpole — Reading chrome

The small things that make long-form reading bearable, all optional and all Postkasse-only.

- Reading time and record length, computed at build.
- Sticky record navigation in single-flowing mode — where am I in a two-hundred-record stream.
- A per-record permalink affordance better than the hover `#`.
- Keyboard navigation between records.

Each is a param defaulting to off, documented in the theme README.

**Acceptance:** each feature demonstrable and each independently switchable off.

### 6 · snail — Attachments render

[schrank item 3](../schrank/ROADMAP.md) decides where attachments live: Hugo leaf page bundles,
files sitting beside `index.md`. This item is the other half — making them look like something.

**The bug that must be fixed first.** In `single` and `single-flowing` modes every record renders on
`/`, so a relative `image.png` resolves to `/image.png` and 404s. Confirmed on the current theme:

```
# single-mode home page, record living at /2026-07-06_23-30/
<img src="image.png" alt="shot">     ← browser asks for /image.png
```

- Fix with Hugo **render hooks** — `_markup/render-image.html` and `render-link.html` prefixing
  `.Page.RelPermalink`, or better, resolving through `.Page.Resources.Get`. Hooks run with page
  context, so all four render spots (page, posts excerpt, single card, flowing article) are fixed by
  one file.
- Raw `<img>` in `unsafe: true` content bypasses render hooks. `book.lua` already works around the
  same limitation with a regex; either mirror that or document the gap plainly.

Then the rendering itself, all Postkasse-only:

- **Video and audio** — `.mp4`, `.webm`, `.ogg`, `.mp3` become real `<video>`/`<audio>` elements
  with `preload="none"`, not broken image icons. No player library.
- **PDF and other documents** — a labelled download affordance with the file's size and type, taken
  from the page resource's own metadata. No embedded viewer.
- **Images** — figure/caption treatment, `loading="lazy"`, intrinsic dimensions from the resource so
  the page does not jump. Hugo's image processing is available in Postkasse (it is not in
  Fuglekasse) — responsive `srcset` is fair game here.
- **An attachment strip** — optionally, the bundle's resources listed at the foot of the record, so
  files that were never linked inline are still reachable.

Books: the PDF and EPUB get whatever `book.lua` can honestly do — images already resolve via
`resolveLocal`, video becomes a labelled link, and that limitation is documented rather than hidden.

**Files:** `themes/Postkasse/layouts/_markup/`, the record partial, theme README.

**Acceptance:** one record carrying an image, a PDF and a video, rendering correctly in **all four**
pageModes — especially `single`, where the relative-path bug lives — and degrading sensibly in the
EPUB.

**Border:** Fuglekasse gets none of this. Not even the render hook.

## Borders for this road

- **Fuglekasse does not grow.** Not one param, not one line of JavaScript, not one partial. If a
  feature is genuinely universal, that argument gets made separately and in the open.
- One build path. `bin/build.sh` and `tools/pandoc/` stay theme-agnostic.
- No service. Search is a static file; RSS is a static file; backlinks are computed at build.
- Taxonomies stay disabled — tags are display-only labels, not links.
