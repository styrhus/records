This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**blyant records** (`codeberg.org/blyant/records`) — a publish-your-conversations site: Markdown transcripts in `records/` are built by Hugo through `bin/build.sh` (the one build path) and published to Codeberg Pages by default, to GitHub/GitLab Pages via shipped shims, or to any pages branch/webroot via `records publish`. Forks publish their own site with zero edits — owner/repo/URL are derived per fork by `bin/build.sh` from CI env; an uncommented `baseURL` in `tools/hugo/hugo.yaml` beats all derivation. See `docs/publish.md`.

## Layout

- `records/` — the content, and the only "data" here. Tracked empty (just `.gitkeep`): the default front page (`content/_index.md`) and the demo record ship in the theme (see **demoMode**), and a site `records/_index.md` shadows the theme's. Records are timestamp-named (`2026-07-06_23-22.md`). 
- `tools/hugo/` — the Hugo site. `hugo.yaml` is the site config (`contentDir: ../../records` — there is no `content/` dir); `one-page.yaml` is the single-mode overlay (see **One-page output**); `baseURL` ships commented (uncommented = authoritative, commented = CI derives per fork).
- `bin/build.sh` — the single build script behind every provider: resolves the site URL (explicit `baseURL` > `BASE_URL` env > `PAGES_HOST` derivation (any git-pages forge) > Codeberg derivation, `pages`-named repo → domain root > `CI_PAGES_URL` > error), exports `PAGES_URL` via `$GITHUB_ENV`, runs Hugo (merging `one-page.yaml` in the single modes), then the book build (skip-noted when pandoc/weasyprint are missing).
- `tools/hugo/themes/Fuglekasse/` — the default theme. Deliberately minimal: flat template system (Hugo ≥ 0.158 — flat layouts need 0.146, `site.Language.Locale` in `baseof.html` needs 0.158 — so `home.html`/`page.html`, no `_default/`), all CSS inline at the top of `layouts/baseof.html`, no assets pipeline, no build step. **Fuglekasse does not grow** — it is minimal by fence, not by accident.
- `tools/hugo/themes/Postkasse/` — the second theme, where growth is allowed: an assets pipeline (`assets/css`, `assets/js`, via `_partials/asset-url.html`) and a mirrored partial contract so every documented param behaves the same. Switch with `theme: Postkasse`. Deliberately still a skeleton — search, backlinks, RSS, reading chrome and attachment render hooks are planned on it, none built. recordkit follows the `theme:` key too: `refs`/`archive`/`verify` resolve theme statics from it (`config.read_theme`, default Fuglekasse, matching `book.lua`), and `records doctor` errors when an explicit `theme:` names no directory under `tools/hugo/themes/`.
- `.ai/skills/` — the conversation skills (`/record`, `/all`, `/me`, `/stick`, `/esc`, `/gc`, `/gcp`, `/phil-gc`, `/cpd`, `/diff-1`, `/diff-3`, `/diff-5`, `/diff-10`, `/diff-20`, `/review`, `/poet`, `/pirate`, `/eq`, `/bff`, `/spellcorrect`, `/werden`); `.claude/skills/` symlinks into it. Skills copied from the user's dotfiles keep their content, but the commit skills (`/gc`, `/gcp`, `/phil-gc`) are simplified to the single repo at `$PWD` — no VSCode multi-root handling, plain `git status`/`git diff` injection, no detect-dirty-repos.sh. The recording skills (`/record`, `/all`, `/me`) and `/cpd` are checkout-aware: they `find` the shallowest `*/hugo/hugo.yaml` (maxdepth 5, dot-dirs and node_modules pruned) from `$PWD` and read its `contentDir` (missing line = `../records`) — so a records clone nested inside another project works from that project's workspace, and inside this repo the probe resolves to `./records` as before. The recording skills write transcripts to the resolved dir, falling back to the old docs-like-dir heuristics when no config is found. `/cpd` runs git as `git -C <checkout>` (no config found = `$PWD`), presents the diff and commit message for confirmation before running, and takes its deploy command from `params.deployCommand` in the discovered `hugo.yaml` (commented by default; unset = a push-triggered workflow in the checkout — `.forgejo/workflows/`, `.github/workflows/` or `.gitlab-ci.yml` — is the deploy, nothing to run; `deployCommand: records publish` is the no-CI hook, and deployCommand is checked first). `/stick` remains `$PWD`-scoped: run it from the records checkout. `/werden` advances the **werden cycle** (German "becoming") — the project's development-cycle version: named `<structure>-<animal>` from the ordered pools in `tools/others/naming/` (`strukturer.json`, structures smallest→largest from `fuglekasse`; `dyr.json`, animals in a size mountain `flue`→`pferd`→`gadfly`; single-token names — hyphens would break the name split), numbered `<epoch>.<major>.<minor>` where epoch is human-owned (hand-edited in `CURRENT`, preserved verbatim) and major/minor are the 1-based pool indices of structure/animal. State is the one-line repo-root `CURRENT`; living docs (`tools/others/README.md`, theme README) carry the greppable marker `<!-- werden: <number> <name> -->`; the root README instead wears the cycle as a single visible line near the bottom, `> Fase — <number> <name>`, renamed by the script. The skill is fully mechanical — no verse, no AI-composed text. Mechanics live in `.ai/skills/werden/werden.sh` (no-arg = animal bump, `<structure>` arg = major step reset to `flue`, `--stamp`/`--here` = re-derive + re-stamp only; it skips `.git`, `node_modules`, `public`, `.mem`, its own dir and `tools/others/python` when stamping) with an AI-free mirror `records werden [structure] [--stamp] [--repo .]` in `recordkit/werden.py`. No changelog; `CURRENT` + markers remain the versioning state, except that release-worthy major steps may carry an annotated git tag referencing the werden name.
- `tools/others/` — an optional AI-free engine and editor plugins that run the *mechanical* skills without a model. `python/` is the deterministic `recordkit` library + `records` CLI (records-dir discovery, tag routing, frontmatter, git/deploy, publish, MPRIS) emitting JSON — `records publish [--dry-run]` builds via `bin/build.sh` and delivers per `params.publishTarget` (`pages-branch` single-commit force-push, or `rsync -az --delete` to `publishDest`); `vscode/` (a sidebar chat view packaged as an installable `.vsix` via `npm run package`), `neovim/` (lazy.nvim-installable) and `emacs/` (`records.el`, one file, mechanical-only) are plugins that call the CLI; `ollama/` documents the local-AI integration. Ollama two-sided `/record` is implemented: `recordkit/ollama.py` (stdlib urllib, pytest-covered with a mocked `_http_post`) exposes `records ollama-reply --endpoint --model --file --human [--timeout] [--context-file …] [--context-dir …]` — it rebuilds the chat history from the record's `## Human`/`## Assistant` sections (signatures stripped), POSTs to `<endpoint>/api/chat` (`stream: false`, 120s default timeout), appends the signed turn via `writer.append_turn`, and appends nothing on failure (`{"error": ...}`, exit 1). Its fileless sibling `records ollama-chat --endpoint --model --human [--history JSON|-] [--timeout] [--context-file …] [--context-dir …]` (`ollama.ephemeral_reply`, recordkit 0.3.0) sends caller-supplied history (`--history` JSON array of `{role: user|assistant, content}`, default `[]`, `-` = stdin via `_stdin_or` — only one flag may be `-` per invocation) plus the new message and prints `{"model", "reply", "appended": false}` without touching disk; invalid history/JSON → `{"error": ...}`, exit 1. The repeatable `--context-file`/`--context-dir` flags feed `ollama.build_context`: file contents (64 KiB/file cap, binary/missing → marker) and directory listings (500 entries, hidden/`node_modules`/`__pycache__`/`.git` skipped), 256 KiB total, injected as a single system message at index 0 for that API call only — model-only, per-turn, never written to the record. The VSCode extension (0.5.0; webview split into `src/webviewContent.ts`, slash registry in `src/commands.ts` feeding both autocomplete and dispatch) reads `records.ollamaEndpoint` + `records.ollamaModel` (both required; captured per-session at `/record` start, so context resets on new recording/`/esc`): messages route through `ollama-reply` with a busy indicator (input locked, no streaming) and fall back to user-only `append` with a warning when Ollama fails; `/all`/`/me` stay user-only; Neovim wiring and voice skills remain future. Without an active recording, messages still chat ephemerally via `ollama-chat` when a model is configured: history lives in `chatHistory` in the provider (piped to the CLI as JSON on stdin, `--history -`; `runCLI` takes an optional `stdinData` arg), is reset on `/record`/`/all`/`/me`/`/esc`, and nothing is written — Ollama failure shows an error with no fallback; no model + no recording shows a dim hint instead of the old "No active recording session." error. Chat UX: messages word-wrap; `/` opens a filtered command popup with argument hints (Tab/Enter accept, Escape dismisses, Enter never submits while open); a gear (⚙) panel writes `records.ollamaEndpoint`/`ollamaModel` to the user settings.json; `@` opens a workspace file/folder picker (`findFiles`, 2000 cap) whose picks become chips passed as `--context-file`/`--context-dir` while the typed `@path` stays in the recorded message; the active-editor file shows as a toggleable context chip (no recorded trace); the active model shows under the input (`model @ endpoint` / `no model — user-only recording`); system/status lines (timestamped, class `status`) render dim (`--vscode-descriptionForeground`) while the `> ` user echo (class `user`) and model replies stay prominent; `ctrl+shift+\` (ctrl+| on US layouts) joins `ctrl+shift+r` on `records.openChat`, which now also focuses the input field (`focus-input` webview message; `pendingFocus` flushed on the webview's `ready` when the view wasn't resolved yet). Covers `/record` setup, `/all`, `/me`, `/esc`, `/stick`, `/gc`, `/gcp`, `/cpd`, `/myname`, `/mucke`, and `/config`. `naming/` holds the werden-cycle name pools + scheme doc (see the `.ai/skills/` bullet). ## Commands

```bash
cd tools/hugo
hugo                 # build to tools/hugo/public/ (gitignored)
hugo server          # local dev at :1313
HUGO_PARAMS_PAGEMODE=single hugo server   # try a param override without editing config
./bin/build.sh [outdir]   # from repo root: full site + books build; needs baseURL, BASE_URL or CI env
```

There are no tests or linters; verification is building and inspecting output. Note: `hugo --quiet` suppresses `WARN` lines — build without it when checking template warnings.

## Architecture

**Config layering.** Theme defaults live in `tools/hugo/themes/Fuglekasse/hugo.toml` `[params]`; the site's `hugo.yaml` `params:` deep-merges over them (site wins); `HUGO_PARAMS_*` env vars override both (CI uses `HUGO_PARAMS_REPOURL`). New theme options must follow this pattern: default in theme toml, read via `site.Params.*`, documented in the theme README and as a commented example in `hugo.yaml`.

**Rendering pipeline.** Records are `## User` / `## Assistant` turns with assistant signature lines (`— model-name`); a named turn `## Human (name)` — written by /record and `append-turn`/`ollama-reply` when /myname has saved a name — renders as a user turn with the name shown. `layouts/_partials/record.html` takes rendered HTML (`.Content` or `.Summary`) and: strips signatures, rewrites relative `records/` links to forge raw URLs (shape per `params.repoLinkStyle`, `auto` = detected from the repoURL host — github.com/gitlab.com/else-Forgejo — branch per `params.repoBranch`; resolution in `_partials/repo-link.html`, mirrored in `book.lua`), and wraps each turn in `<section class="user|assistant">` for styling. All record display — single pages (`page.html`), the posts-mode excerpts, and single-mode cards (`home.html`) — must go through this partial.

**Publishing.** `bin/build.sh` is the one build path; the CI shims are logic-free and host-guarded: `.forgejo/workflows/pages.yml` (Codeberg, or any Forgejo whose admin sets the instance Actions vars `PAGES_HOST`/`PAGES_RUNNER` — plus optional `PAGES_SERVER`/`FORGE_URL`/`RUNNER_IMAGE` for in-cluster runners and `PAGES_ACTION` for an instance-local action mirror; git-pages action), `.github/workflows/pages.yml` (configure-pages `base_url` → pages artifact), `.gitlab-ci.yml` (`CI_PAGES_URL`). No-CI delivery is `records publish`; its params (`publishTarget`/`publishBranch`/`publishRemote`/`publishDest`) ship commented in `hugo.yaml` next to `deployCommand` and are read by tooling only, never by templates. User docs + fork migration notes: `docs/publish.md`.

**pageMode.** `params.pageMode` switches the home page: `basic` (link index, default), `posts` (latest `postsCount` excerpts with Read-more), `single` (one-page site: `_index.md` card first, then every record ascending as a document card; no auto links to records), `single-flowing` (one continuous conversation: only the Human/Assistant turns, no titles/tags/dates/chapters, records split by a `· · ·` divider, ordered by `singleOrder`; PDF/EPUB follow suit). `home.html` warns and falls back to basic on unknown values; `baseof.html` tags `<main class="mode-…">` for the CSS.

**One-page output.** The two single modes publish only `index.html` — no per-record pages, no `sitemap.xml`. Hugo config can't branch on its own params, so `bin/build.sh` merges `tools/hugo/one-page.yaml` (`--config hugo.yaml,one-page.yaml`) when `pageMode` is `single`/`single-flowing`: a `cascade` catch-all `kind: page` → `build: {render: link}` (`link`, not `never` — `never` empties `.RelPermalink`, which all anchor ids derive from) plus `disableKinds: […, sitemap]`. List keys replace across config files, so the overlay restates `hugo.yaml`'s `cascade`/`disableKinds` in full (both marked `MIRRORED`); first cascade match wins, so the `/license` exemption precedes the catch-all. Attachments beside a record still publish; a page opts back in with `build: {render: always}` in its front matter; a hand-run `hugo server` skips the merge.

**demoMode.** `params.demoMode` (theme default `false`; the site sets `true`) renders theme-shipped demo records — content files with `demo: true` front matter (the theme ships `content/example/example-recording.md`, merged via Hugo's theme-content union like `content/404.md`) — only while the site has no real records: gated once in `home.html` right after the `$all` chokepoint (`$real := where $all "Params.demo" "!=" true`; `$all` keeps the demo set only when demoMode is on and `$real` is empty). Auto-hide means zero-edit forks inherit `demoMode: true` safely — their first record hides the demo. The theme's `content/_index.md` (welcome front page) is not demo-gated: a site `records/_index.md` shadows it, like the 404 page. Hidden demo pages keep their direct URLs and sitemap entries; demo content never reaches the PDF/EPUB (`book.lua` reads `records/` from disk only). `demo` is a reserved front-matter key.

**Filter.** `params.showFilter` (theme default `false`, opt-in; honoured in single mode only — other modes `warnf` and ignore it) renders a client-side record filter on the single home page: a fixed funnel button bottom-left (`details.filter`; class `beside-spotify` shifts it to `left: 2.75rem` when `params.spotify` is set, else it takes Spotify's `left: 1rem` spot) whose panel opens upward like the Spotify player. `home.html` renders it via the inline partial `inline/filter.html` fed `$all`, which builds sorted/deduped tag and language vocabularies at template time — the language fieldset only renders when some record sets `language:`, with a `(none)` checkbox when some record doesn't — plus always-present from/to date inputs, a `Word` search input (last group, nearest the button) and a Clear button (no submit; no-JS leaves a plain `<details>` with inert controls). Cards carry the machine-readable state: `inline/record-card.html` emits unconditional `data-date="YYYY-MM-DD"` (also the intro discriminator — the `_index` card has none, so the JS selector `article.record-page[data-date]` never touches it) and `data-tags="a,b"` (independent of `showTags`); language reuses the `lang` attribute (absent = the `none` bucket; comma-in-tag unsupported). The JS sits in the `baseof.html` IIFE, gated on `details.filter` existing: groups (tags, languages, date range, word) AND together, tags/languages match-any, dates inclusive by lexicographic compare on `data-date`, word compiled as a case-insensitive regex (invalid syntax regex-escaped to a literal) and tested against the card's whitespace-collapsed `textContent`, cached once as a `wordText` expando; the word input re-filters live on `input` (`change` alone fires only on blur/Enter), and matches in visible cards get an accent tint via the Custom Highlight API (`::highlight(word-match)` rule in `baseof.html`; browsers without the API filter untinted); non-matching cards get `.filter-hidden` (`display: none`), chapters with no visible card hide too, chapters with matches force-open while a filter is active (pre-filter fold remembered once in `dataset.filterOpen`, restored on clear). State syncs two-way with the URL — `?tags=a,b&language=nb,none&from=…&to=…&word=…`, parsed via `URLSearchParams` on load (prefills the controls), written back hand-serialized (commas literal, `word` `encodeURIComponent`ed) via `history.replaceState` with the hash preserved; cleared groups drop their params. The popper joins the click-outside close list; `revealHashTarget` is untouched — filter wins, a hash to a filtered-out card just doesn't scroll. `book.lua`/PDF/EPUB are untouched (view-only feature).

**Comment links.** `params.commentURL` (theme default unset/commented) points at a forge new-issue endpoint and renders a per-record `Comment` link (a `.post-date`-styled `<p>`) via `_partials/comment-link.html` — called from `page.html` and the single-mode `inline/record-card.html`, after the date line. The link href is `<commentURL>?title=[<site> - #<slug>]: ` (`querify`-encoded); `<site>` is `params.commentSite` else the `baseURL` host (`urls.Parse`), `<slug>` is `path.Base .RelPermalink`. `LICENSE.md` is skipped inside the partial (it renders through `page.html`; other render spots only see records). Not rendered in posts/basic/single-flowing, never in the PDF/EPUB. This exists so forks like tb4-rot don't need site-level `layouts/` overrides for their Comment links — overrides shadow the theme wholesale and go stale (the cause of the "filter didn't show up on i.xil.no" bug, 2026-07-28).

**Content conventions.** The explicit `date:` frontmatter field is authoritative for ordering (`frontmatter.date: [':default', ':filename']`); the filename is only a fallback for records without a `date:` field, so a record's position never depends on its filename. All three pageModes order by `.Date` (index modes newest-first, single mode oldest-first). Permalinks use the full `:contentbasename` (time-only slugs would collide across days). Frontmatter flags: `draft: true` (archetype default; kept out of the site), `featured: true` (pinned to top of index, set by `/stick`), `showDate: false` (hides that page's `.post-date` line in all three render spots; 404.md sets it). A file named `records/LICENSE.md` gets a footer link (link text = its `title:`, any value; falls back to "License") and is excluded from record lists — both keyed on the filename, not the title. `tags: [a, b]` renders as dim display-only `#a #b` labels (`.post-tags`, above `.post-date`) in the same three render spots; `params.showTags` (theme default `true`) toggles them site-wide, `showTags: false` opts a page out; taxonomies stay disabled, so tags never become links. `/record #tag Title` (also `/all`, `/me`) files the record under `records/<first-tag>/` with the remaining text as title and all tags in frontmatter; `/stick` resolves slugs folder-aware via `find`. A site-config `cascade` in `hugo.yaml` targets `kind: section` with `build.render/list: never`, so folder URLs like `/linux/` 404 (and no section-template WARN) while records inside keep `/linux/<slug>/` URLs. The 404 page is content: the theme ships `content/404.md` (merged under the site content by Hugo's mounts; a `records/404.md` shadows it). A content file at path `/404` shadows Hugo's standalone 404 kind — that's why the file itself must carry `url: /404.html`, `layout: "404"`, and `build.list: never`, and overrides must keep that front matter block. The built `404.html` is what Codeberg Pages serves for missing URLs. `params.dateTitleFormat` (unset in the theme; the site sets `"02. January 2006"`) renders timestamp-fallback titles as `.Date` formatted with that Go layout — in `page.html`, all three home modes, and the `<title>` tag; hand-written titles are never reformatted. `params.datePostFormat` (unset in the theme; the site sets `"02. January 2006 15:04"`) adds a bottom-right `.post-date` line with the formatted `.Date` to record pages and posts/single-mode cards; unset shows none.

**Generator meta.** `hugo.yaml` sets `disableHugoGeneratorInject: true` and a `module.mounts` entry mounting the repo-root `CURRENT` into `assets/CURRENT` (Hugo's `readFile` can't leave the project dir; the legacy `contentDir`/`staticDir`/`dataDir` keys coexist with the mount). Both themes' `baseof.html` emit `<meta name="generator" content="blyant records <version>">` on every page — `<version>` is the first field of `CURRENT` via `resources.Get "CURRENT"`, `with`-guarded so a missing file just drops the tag. Nothing to bump on werden turns: the tag reads `CURRENT` at build time.

**Deliberate omissions.** RSS and taxonomies are disabled in `hugo.yaml` — the embedded RSS template would leak signature lines through summaries. Goldmark `unsafe: true` is intentional (records are trusted first-party content).

## Conventions

- Keep the theme minimal: flat templates, a handful of partials, inline CSS, no build tooling. Resist adding partials, JS, or asset pipelines.
- `records/` markdown is user content — don't edit records except via the skills or on explicit request.

## Editing this file

This file (`CLAUDE.local.md`) may be edited without asking for confirmation. Keep it accurate: when a change alters documented behavior — config keys, ordering, pageModes, the rendering pipeline — update the matching section in the same turn.

The working `CLAUDE.local.md` is gitignored (`*.local.md`), so edits to it are never committed. To keep a change in version control (and reach forks), mirror it into the tracked `CLAUDE.local.md.example.md` in the same turn — matching that file's shorter, genericized tone rather than pasting full private detail.
